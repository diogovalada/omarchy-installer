# Configurable PC startup menu

Date: 2026-09-06. Development implementation; boot execution remains unqualified.

The user approved a menu at normal PC startup, initially selecting Omarchy after
five seconds, with preferred OS and timeout configurable in our installer. The
user also requested a durable record of cross-platform differences for users and
the wider team. That reference is [platform behavior](../platform-behavior.md).

The frontend exposes Omarchy/Windows and 5/10/15/30-second choices, explains the
temporary startup selection and Windows' extra restart, and sends typed settings
through Rust, the elevated helper, construction manifest and exact native plan
approval. USB creation does not accept these settings. The Mac panel explains
Apple's startup picker and required Recovery completion instead.

The constructed image reuses its upstream-generated normal kernel entry for the
primary Omarchy choice, retains upstream kernels/snapshots as advanced options,
and uses `efi_boot_entry` for Windows. The installed hooks preserve settings and
handle the machine-ID transition before first hardware/factory-reset updates.
They validate the mounted EFI partition, write the config atomically with a
previous-file backup, and run within the upstream tool's operation lock before
config enrollment. Construction validates the installed settings, hook bytes,
EFI identity and resulting menu. These construction checks are implemented but
have not been executed in a VM for this change.

Native Windows preparation requires one unambiguous Windows Boot Manager entry
bound to the current system EFI partition and rejects a pending one-time boot.
Deployment rechecks its entry/order hashes, saves the previous order in the
protected journal and prepends the OS menu while retaining all prior entries.
Readback verifies both writes. A failed order write is rolled back only when the
current value still equals the value written by this operation. Firmware has no
atomic compare-and-set; unknown concurrent changes remain a recovery case.

The actual pinned ISO was inspected read-only. It contains Limine 12.6.0-1 and
limine-mkinitcpio-hook 1.37.1-1; both package hashes are added to the source lock.
The package documentation and the update tool's 1.37.1 source were reviewed for
configuration, hooks and machine-ID ownership. No upstream distribution code was
changed, and no host boot variables were inspected or written during this work.

Validation passed: frontend type check (zero errors, four pre-existing warnings),
Rust formatting/library check, PowerShell 5.1 syntax parsing and C# compilation,
Python AST parsing, Bash syntax and embedded Python parsing, and the Windows
native build. The [build record](boot-menu-build-2026-09-06.json) records hashes.

Following the user's earlier instruction to defer testing, no new test suite,
UI execution, image-construction VM, disk probe, elevation, partition/firmware
mutation, BitLocker operation, reboot or boot validation was performed. Windows
menu/default/timeout, kernel/snapshot updates, owner rekey, firmware recovery and
BitLocker combinations still require execution qualification. Mac compilation,
signed packaging and hardware qualification remain pending.
