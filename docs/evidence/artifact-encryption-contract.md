# Transient encrypted artifact contract

Implementation provenance: **gpt-6-astra**, 2026-09-06. This contract covers the
temporary image files used between isolated construction and native deployment.
It is separate from the installed root filesystem's LUKS2 encryption and the
user's permanent unlock passphrase. Runtime cryptographic interoperability,
test vectors, image builds and hardware qualification are explicitly deferred.

## Operation key and lifetime

The native helper creates a fresh cryptographically random 32-byte operation key
for each construction/deployment operation. The same key is available only in
process memory to the helper, its authenticated PowerShell subprocess, and the
isolated builder. Transport uses private stdin pipes; it must not use command
arguments, environment variables, JSON files, log records, receipts, recovery
notes or host-storage key files. The Python exporter supplies OpenSSL's password
through an inherited anonymous descriptor, not a filesystem object.

Keys are erased from mutable temporary buffers where the implementation owns
them. The helper owns the original operation key and destroys it when the
operation ends. No recovery key is persisted for these temporary envelopes;
encrypted construction files left after process loss require a fresh build.
Managed runtimes and OS memory behavior prevent claiming that every internal
copy has been formally zeroized. These modules do not intentionally persist
keys or plaintext images; caller isolation and host memory policy remain
separate responsibilities.

## Exact envelope

```text
offset  length  content
0       8       ASCII "Salted__"
8       8       independent random salt generated by OpenSSL
16      rest    AES-256-CBC ciphertext with PKCS7 padding
```

The password for PBKDF2 is standard padded Base64 of the raw 32-byte operation
key, encoded as ASCII: exactly 44 bytes. A newline terminates OpenSSL's private
password pipe; the newline is not part of the KDF password. Derive **48 bytes**
using PBKDF2-HMAC-SHA256 with the envelope's eight-byte salt and **100000**
iterations. Bytes 0–31 are the AES key; bytes 32–47 are the CBC IV.

The independent authentication key is:

```text
macKey = HMAC-SHA256(key=rawOperationKey,
                    message=ASCII("omarchy-artifact-mac-v1"))
tag = HMAC-SHA256(key=macKey, message=entireStoredCiphertextFile)
```

The tag authenticates the complete file, including the 16-byte magic/salt header.
Tags and SHA-256 values are represented as 64 lowercase hexadecimal characters.
Before CBC decryption exposes plaintext, the Windows decoder must verify both
this tag and the manifest's stored SHA-256 over the same opened ciphertext
descriptor. The manifest is part of the protected, hash-bound operation plan;
the unkeyed stored SHA-256 alone is not authentication.

For a plaintext length `n`, the exact stored size is
`16 + 16 * (floor(n / 16) + 1)`. PKCS7 adds a complete padding block when `n` is
already block-aligned. Plaintext lengths are positive and at most 64 GiB for this
fixed construction recipe. Decoder iterations and algorithm are fixed; the
manifest parser must reject alternate values rather than treating them as
arbitrary cryptographic options.

The current image runtime pins OpenSSL **3.0.13**. It uses the historical
eight-byte `enc` salt and default PKCS7 padding; the exporter explicitly selects
AES-256-CBC, PBKDF2, SHA-256 and the iteration count, then validates the expected
header and stored size. OpenSSL documents these switches and its eight-byte
default salt. [OpenSSL enc documentation](https://docs.openssl.org/3.0/man1/openssl-enc/)
The .NET implementation uses the SHA-256 constructor of `Rfc2898DeriveBytes`
and requests the full 48-byte key/IV material in one operation.
[Microsoft Rfc2898DeriveBytes documentation](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.rfc2898derivebytes)

## Manifest shape

Each output keeps the ordinary image's size and SHA-256 separate from storage
encryption. The Python writer returns this shape, with caller-supplied role/GUID
fields added elsewhere by the builder:

```json
{
  "file": "root.img.enc",
  "sizeBytes": 40800092160,
  "sha256": "<SHA-256 of the original plaintext image bytes>",
  "envelope": {
    "format": "openssl-aes-256-cbc-pbkdf2-sha256",
    "iterations": 100000,
    "hmacSha256": "<HMAC-SHA256 of the entire stored file>",
    "storedSizeBytes": 40800092192,
    "storedSha256": "<SHA-256 of the entire stored file>"
  }
}
```

No secret is a manifest field. `esp.img.enc` uses the same envelope. The clear
root image is itself an intact LUKS2 volume; decrypting this temporary envelope
does not unlock its filesystem. Its clear-image SHA-256 hashes the complete LUKS2
partition image, including encrypted filesystem bytes and LUKS metadata.

## Python producer API

```python
encrypt_image(output_path, key, chunks, total_size,
              operation_id, role, check_cancel, on_progress=None) -> dict
```

`chunks` yields nonempty byte buffers of at most 1 MiB from a readonly image
stream. `role` is `esp` or `root`; the new absolute output filename must match
`<role>.img.enc`. The caller never materializes a plaintext image on host
storage. Cancellation checks run during input, pipe backpressure, process
finalization and ciphertext hashing. The progress callback receives only a
count of plaintext bytes supplied to encryption. Exceptions cancel export and
prevent a receipt. The exporter closes/reaps OpenSSL, erases its owned mutable
secret buffers, and removes only its own unfinished ciphertext file.

Ciphertext is written directly by OpenSSL into an exclusively created regular
file, synchronized, then fully reread through its original descriptor to compute
stored SHA-256 and HMAC. Its algorithm options are fixed; no caller-controlled
executable, shell command, cipher selector or password source is accepted.

## Windows decoder API

```csharp
Stream EncryptedImage.Open(path, plaintextLength, storedLength,
                           storedSha256, hmacSha256, rawKey);
void EncryptedImage.ValidateHash(path, plaintextLength, storedLength,
                                 storedSha256, hmacSha256,
                                 plaintextSha256, rawKey);
string EncryptedImage.InspectLuksHeader(Stream plaintext);
```

All types live in `Omarchy.DirectX86`. `Open` authenticates the complete
ciphertext before returning a forward-only read stream, using a `FileShare.Read`
descriptor held throughout decryption. It rejects links, network/device paths,
incorrect sizes and unsupported envelope headers. Returned `Length` is the
manifest's plaintext length; final padding and EOF are checked before returning
the last image bytes. Each read is bounded to at most 1 MiB.

Before allocation or writing, the caller must run `ValidateHash` for **both**
images. It fully decrypts and checks the original plaintext SHA-256 and length.
Deployment then calls a fresh `Open`; that call reauthenticates the same expected
stored file before handing its retained descriptor to the native writer. The
writer must enforce partition/image bounds and perform its ordinary full
destination readback. Encryption does not replace any disk-policy validation.

`Open` and `ValidateHash` also have overloads accepting cancellation and progress
callbacks for pre-allocation work. Do not use an interruptible read callback
once a native deployment has entered its noninterruptible disk-writing phase.

`InspectLuksHeader` consumes the first 512 plaintext bytes and checks the primary
LUKS2 magic/version and UUID field at byte offset 168. It returns a canonical UUID
for comparison with the construction manifest. Use a fresh `Open` for the actual
write. This is a bounded identity check, not a claim that all LUKS metadata or the
enclosed filesystem was independently qualified.
